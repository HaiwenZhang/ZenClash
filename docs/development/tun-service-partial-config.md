## 问题与行为目标

原先直接转发 `PATCH /configs` 只改变内核，服务持有的正式配置和已提交 revision 没有同步。服务端现在拒绝通用 API 的配置 PATCH 绕过，使用具名候选事务；core 新接入阶段已覆盖业务保存、备份目标合并及首审恢复问题。模式修改保存成功后，重启必须保留新模式，待重试备份也不能覆盖后来保存的设置；部分更新不得重新读取变化中的订阅和覆盖源，将未应用内容混入启动缓存。

局部修改继续采用内核 PATCH，保持无关连接、provider 缓存、节点身份和资源路径。准备候选、应用、业务保存与提交确认形成同一个受控事务。配置结构或资源发生完整变化时，继续使用已有完整配置事务。

## 协议与迁移

内部协议升级到 v2，新增经过同一原生身份核验、会话凭证、generation 和请求序号校验的操作：

| 操作 | 行为 |
| --- | --- |
| `PrepareRuntimePatch` | 给定已接受的 base revision 和受限 patch，生成候选配置并返回 revision；不修改内核 |
| `ApplyRuntimePatch` | 向同一受管内核发送局部 PATCH，并回读受影响字段 |
| `RestoreRuntimePatch` | 对尚未保存的候选，运行时恢复已持有的旧字段并回读；确认内核已停止时清理候选配置，保留 accepted 与共享资源 |
| `CommitRuntime` | 业务保存成功后幂等确认候选，沿用现有提交入口 |
| `Status` | 返回应用/提交 revision，以及候选的 base、类型和阶段；未知修改只通过回读核实 |

候选阶段区分 Prepared、Validated、Applied 和 Uncertain；完整候选与部分候选具有明确类型。相同 base 与规范化 patch 的重复准备返回原候选，不改变其阶段。不同请求不能覆盖等待确认或结果未知的候选。原始 API 的配置 PATCH 不能绕过该事务。

局部操作必须匹配固定 Mihomo 版本的实际接口。TUN 参数修改未明确请求 enable 时，使用同 PID 的新鲜回读保持原开启状态，应用、逆向修改、核验和正式 YAML 都涵盖该字段；重复准备仍按原请求判断。仅对已确认的 GET 省略字段归一化默认值，缺少必需观察时不发送修改。固定版本不支持局部 PATCH 的字段继续走现有完整配置事务，不能由测试替身假装局部支持，也不能关闭已有界面功能。

当前固定版本为 Mihomo `v1.19.30`。`unified-delay`、`inbound-tfo`、`inbound-mptcp`、`disable-keep-alive`、`keep-alive-interval`、`keep-alive-idle`、`routing-mark` 不走原生局部 PATCH。默认值归一化仅用于已确认的 TUN 对象；观察到的 MTU 0 可用于准确逆向恢复，不能因此放宽用户局部修改的 MTU 校验。

core 接入区分用于幂等判断的原始请求与最终实际应用的 delta。新阶段已接通安全 effective delta 响应，将服务补齐的 enable 和规范化后的字段同步到 accepted bundle、启动缓存和备份恢复目标；仅合并原请求不能证明一致。响应不含配置秘密或文件路径，实际调度边界测试与本阶段最终审查通过。

旧协议服务不能接受 v2 控制请求。旧安装元数据仍可读取，用于诊断和显式修复；安装元数据 schema、用户数据库、订阅文件格式均不改变。修复部署新 helper 后才允许恢复控制，不静默操作旧协议内核。不新增第三方依赖。

## 配置与资源所有权

每个 revision 独立保存有界正式 YAML。部分候选从已经接受的配置生成，复用其已持有的资源；不重新上传、不复制整包，也不改变 provider 或证书路径。正式 YAML 保留服务生成的控制器地址和秘密，不将秘密返回客户端。

上传输入与准备资源作为共享资源组，与 revision 的配置目录分别管理。删除旧配置不能删除新候选仍使用的资源。清理由服务状态所有者显式执行，不能在 `Arc` 析构中执行目录 I/O。保留 active、单个 candidate 和有界待清理槽；清理失败阻止扩大暂存数量，不积累 revision 链。

控制器回读必须属于原受管内核。PID 改变、停止或回读失败不能证明修改没有发送，也不能证明已应用。成功回读只核实受影响字段，不把主配置中未回读的字段宣称为内核事实。

## 保存、取消与未知结果

准备失败或确认零发送：清理候选，恢复本次缓存，不发送内核回滚。

PATCH 已发送而响应丢失：保留候选和旧字段，通过同一内核的 GET 区分旧值、新值与未知；不能盲目重新发送 PATCH、重新 Stage 或启动第二个内核。

应用已确认但业务保存失败：仅对持有的旧字段执行逆 PATCH 并回读。恢复仍未知时保留两份准确状态和恢复权限，不报告成功。

业务保存成功：接受新的配置与资源快照，再进行提交确认。确认丢失时仅查询状态或重试幂等提交；调用方取消等待不触发回滚，不丢弃已保存配置。退出协调等待已准入的事务收尾，再停止实际所有者。

core 的部分更新缓存从已接受的完整运行配置推导，只合并本次实际应用并成功保存的字段，不重新合并变化中的用户源。既有覆盖规则仍需准确校验本次意图，不能默默越过有序覆盖的约束。

## 备份恢复一致性

待重试的备份恢复保留旧资源字节。后来成功保存的部分修改，需要同时合并到恢复目标的业务 payload 和服务 YAML，并更新 generation。不能用整个新候选替换旧资源，也不能仅删除恢复上下文来绕过一致性问题。

未发送、保存失败或尚未确认业务保存的修改不能被当作成功 delta 合并。业务已保存、仅提交确认未知时，仍须保留并合并已保存 delta；使用明确的保存收据判断，不能只依据返回值是否为 `Ok`。恢复目标采用有界合并快照，不保存无限历史。重试仍遵守 Finalizing 确认与恢复权限隔离。

## 验证目标

本阶段已有三项先失败再通过的业务回归：源配置变化不混入已接受缓存、取消等待不拆散业务保存与缓存更新、旧备份重试保留后来保存的模式。另有五项受控服务事务边界测试通过，覆盖共享资源与 effective delta、提交确认丢失、逆 PATCH、应用响应丢失及准备响应丢失。这些证据不包含首次安装工作流或真实 Mihomo。

首审恢复问题已修复：准备 PATCH 后内核明确停止，或准备响应丢失后停止，均先用现有 Restore 清理未保存候选，再用新鲜 Status 确认 candidate 已消失、committed base 保留且内核停止。此路径不 Commit(base)，随后重启只启动 accepted；恢复响应丢失也以 Status 核实。core 四项停止恢复行为和 service 两项候选清理/失败重试行为通过，第二轮审查通过。清理失败保留 staged/retired 所有者；已保存及 Finalizing 候选不能回退，状态未知不能盲重发 PATCH 或启动第二份内核。协议仍为 v2，没有新增 Discard 操作。

- 实际局部请求更新指定字段，PID、无关连接和资源路径保持一致；不发生 PUT、全量 reload 或资源重上传。
- 正式 YAML、应用 revision、业务保存和提交 revision 一致；重启只使用已接受配置。
- 订阅/覆盖源变化或删除后仍使用准确的已接受内容，失败恢复保持原资源字节。
- prepare、apply、restore、commit 的响应丢失按阶段处理；未知状态不重复发送修改。
- 保存失败执行逆 PATCH；保存成功而确认丢失保留结果；取消等待和退出不制造并行保存/回滚。
- 备份恢复失败后修改模式，再重试恢复：旧资源保留，新模式不被覆盖。
- 部分候选与完整候选的清理不会误删共享资源；残留与预算耗尽不会积累目录。
- v1 安装信息可用于修复，但不能握手控制 v2；新元数据和协议一致。

状态机与受控 HTTP fixture 只证明事务行为。真实 Mihomo 的局部更新、连接保留、服务重启和三平台授权仍须按计划分别验收。
