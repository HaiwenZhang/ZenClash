# 完整应用响应性探针

此探针运行当前工作区的完整 `ZenClashApp`，包含真实 Mihomo、后台刷新、托盘、配置表单、日志和流量历史。仅支持 macOS。它补充页面级探针，不是 release 帧率基准，也不模拟用户鼠标输入。

## 隔离与源码差异

[`full_app_probe.py`](../../scripts/diagnostics/full_app_probe.py) 将当前 `crates`、`platforms`、Cargo 清单和锁文件复制到新建的临时目录。默认只做三种诊断修改：

- 五处 macOS 默认应用数据目录改为该临时目录；脚本核对文件集合和替换次数，不改动原工作区或用户的 HOME。
- 可执行文件改名为 `zenclash-full-app-probe`，避免覆盖正常开发可执行文件。
- 窗口创建后启动自动导航与计时，最后调用生产 `begin_quit`。

生成配置含 500 个 direct 适配器和 20 个 select 组，无私人订阅或远程节点地址。诊断应用的系统代理偏好关闭、无所有权凭据，生成配置的 TUN 关闭；主机已有系统代理不属于该断言。内核数据通过 `ZENCLASH_CORE_HOME` 指向临时目录。数据根目录之外的原生系统状态检测仍执行，因此此环境不等于另一台独立操作系统。

## 复现

从工作区根目录执行，Mihomo 路径按本机安装位置调整：

```sh
python3 scripts/diagnostics/full_app_probe.py > /tmp/zenclash-full-app-probe.json
probe_root=$(python3 -c 'import json; print(json.load(open("/tmp/zenclash-full-app-probe.json"))["root"])')
CARGO_TARGET_DIR="$PWD/target" cargo build \
  --manifest-path "$probe_root/source/Cargo.toml" \
  -p zenclash-ui --bin zenclash-full-app-probe --locked --offline

env -u ZENCLASH_CONTROLLER -u ZENCLASH_SECRET \
  ZENCLASH_CORE=mihomo \
  ZENCLASH_CORE_BINARY=/Applications/ZenClash.app/Contents/Resources/mihomo \
  ZENCLASH_CONFIG="$probe_root/fixture.yaml" \
  ZENCLASH_CORE_HOME="$probe_root/core-home" \
  "$PWD/target/debug/zenclash-full-app-probe" > "$probe_root/run.log" 2>&1
```

脚本可接受 `--nodes` 和 `--idle-seconds`。默认隐藏 180 秒，隐藏期间不增加诊断轮询，完整应用自身后台工作继续执行。切页顺序为代理组、连接、日志、设置、DNS、首页；隐藏前停在设置，恢复后先进入代理组，再重复同一顺序。结束后正常退出。

保留 `probe.json`、`run.log` 和源码副本以便检查；它们不是永久应用数据。程序异常退出时，先按临时目录的唯一名称确认对应内核 PID，再清理该测试进程。macOS `ps` 的 `comm` 列可能截断；核对时应使用 `ps -ww -axo pid=,command=`，只报告匹配测试目录的结果，避免输出其他进程的参数和凭据。

## 指标解释

- `probe_navigation`：生产页面导航函数同步调用耗时。
- `probe_next_frame`：导航开始至 GPUI `on_next_frame` 回调的时间；不是页面所有后台请求完成时间，也不是显示器实际呈现或输入反馈延迟。
- `probe_active_gap`：导航后一秒内，50 ms 定时回调的最大实际间隔，包含正常等待的 50 ms。
- `probe_hidden` / `probe_reactivated`：隐藏与恢复边界。
- `probe_request_normal_quit`：请求正常退出；还需检查进程实际结束以及测试内核是否残留。

节点均为生成的 direct 适配器，没有真实代理负载。默认模式的连接页不含大量活动连接，未点击测速或编辑表单，未开启系统代理或 TUN，也未模拟睡眠唤醒。因此未出现停顿不能证明用户报告的“系统代理开启、切后台后首次进入代理组卡十几秒”已解决。还需 Windows 及对应真实流量条件下的采样。

## 真实活动连接与程序化搜索

可用 `--connections 1000 --idle-seconds 30` 准备带连接负载的副本。此模式额外在诊断副本中加入本机 TCP 服务、HTTP CONNECT 客户端及输入/结果检查方法，生产工作区文件不变；其他编译、运行方式相同。

测试先读取真实内核的实际 mixed-port，然后通过该代理端口向临时本机服务建立连接，发送少量数据并保持连接。控制器确认活动连接数等于 1000 后开始切页。连接页通过生产 `InputState::set_value` 发出输入事件，经过生产订阅、80 ms 合并、后台筛选和展示投影；检查快照为 1000 条、匹配数为 1000 或 0、所有索引属于相应快照，连续修改后结果对应最后查询。

1000 条连接涉及客户端、内核和服务端的多个文件描述符。运行前可在专用子 shell 中执行 `ulimit -n 8192`，再运行诊断命令；不要全局修改系统限制。此次由 Python 启动器仅提高其自身及子进程的软限制至 8192（不超过硬限制）。

2026-09-12 实测，macOS / ARM64，真实 Mihomo v1.19.30，500 节点/20 组/1000 活动连接：

| 指标 | 结果 |
| --- | ---: |
| 两轮搜索结果检查 | 6 次通过 |
| 程序化输入调用最大耗时 | 22 µs |
| 三次连续改词开始至最终结果可用 | 129.059–163.662 ms |
| 全部切页观察段 50 ms 定时回调最大间隔 | 93.673 ms |

改词之间等待 20 ms，结果每 20 ms 检查一次；搜索总耗时包含这些等待和生产 80 ms 合并时间，不能当成纯 CPU 筛选时间。程序化输入调用不包含 OS 键盘事件分发，也不能当成用户可感知的输入反馈延迟。最大定时回调间隔高于无连接基线，但只有单次运行，尚不能定位是哪段工作或计算稳定回归比例。

运行正常退出（退出码 0），完整命令列检查无对应测试内核残留。此模式有真实本机代理连接，但未开启系统代理，没有持续大吞吐外部流量；隐藏时间为 30 秒，不替代前一节三分钟场景。还需实际键盘交互、真实网络流量及 Windows 验收。

## 实际输入交互验收（2026-09-12）

新增 `--interactive-seconds 180`：自动场景结束后停在连接页，保留窗口供实际交互，随后请求正常退出。为使原生 UI 工具识别，测试将诊断可执行文件复制到临时 `.app/Contents/MacOS`，使用独立 `CFBundleIdentifier=org.zenclash.diagnostic`；没有修改正式安装包或发布流程。连接负载与数据目录仍来自隔离副本。

原生 UI 工具读到的 AX 树只有窗口级节点，故依据当前截图定位输入框，再发送选择全部、文本输入和方向键操作。截图确认：

- 输入 `no-match-fixture` 后显示 `0 / 1000` 和“没有匹配的连接”。
- 输入 `127.0.0.1` 后恢复 `1000 / 1000`，输入框保留焦点。
- 连续替换为不匹配文本后再改回匹配文本，最终稳定为 `1000 / 1000`，“正在更新连接列表…”提示消失。
- 通过 Cmd+Q 正常退出；按临时目录检查，诊断应用和对应 Mihomo 均无残留。

这验证了可见结果和基本输入焦点行为，未测量输入事件至显示器呈现的延迟，也不覆盖中文 IME、全部快捷键或大吞吐流量。

此轮还发现一个未解释的启动差异：直接启动临时 `.app` 中的可执行文件时，自动搜索探针在三秒内未收敛并中止；该轮没有记录到预期的下一帧回调。随后 UI 工具取得的可见实例可以完成上述输入操作。UI 工具的首次窗口读取异常耗时，因此不能把两者当成同一次正常自动运行，也不能把后续交互成功当作前述失败的修复。后续应记录窗口首次绘制/激活、页面数据就绪和投影状态，再区分探针启动前提不足与应用恢复问题；不得简单放宽超时掩盖失败。

## 启动/激活诊断补充

探针现记录每次导航时的 `window.is_window_active()`；搜索三秒超时时记录页面、窗口可见性状态、加载状态、连接快照数量、当前查询、是否正在投影及已有投影查询/结果数。仅打印夹具相关状态，不输出控制器密钥。

2026-09-12 再次直接运行临时打包应用（1000 条连接、隐藏 1 秒），保持原三秒搜索超时：12 次导航、6 次搜索检查通过，搜索总时间 124.983–146.139 ms；正常退出码 0，无对应进程残留。12 次导航中 11 次窗口活跃，恢复后立即进入代理组的那次为 `active=false`，随后进入连接页时已为 `active=true`，两轮搜索均在活跃窗口下执行。

这确认激活请求和原生窗口激活是异步过程。运行时 `switch_to` 仅在实时更新已启用时发起读取，窗口重新激活会刷新可见页。这是前一次打包探针失败的可能解释，但首次失败没有窗口/投影诊断记录，本次又未复现，故仍不能认定根因或将其标为已修复。不增加超时或修改生产暂停策略来让探针通过。

## 系统代理状态的结论边界

此前“系统代理关闭”的表述仅有应用偏好和无所有权凭据作为证据，不能代表主机系统代理实际关闭。所有隔离探针均不主动接管或清除主机已有代理，也未记录原故障条件下的主机代理状态与控制器归属。应将结论限定为“诊断应用未接管系统代理”，仍需在明确记录系统实际状态的场景下验收。该澄清不改变已有连接/搜索计时数据，但限制其适用场景。
